01 Executive summary

TalentAI is a cleanly layered, well-tested Spring Boot + React application whose architecture is sound and whose correctness is strong. Its current limits are operational: single-instance deployment, an untuned connection pool, no caching or asynchronous processing, and a handful of inefficient aggregation/mapping paths. None require redesign — they are configuration and localized-code improvements.

Strength

Clean layering

Controller → Service → Repository throughout, DTO-bound, Flyway-owned schema, 133 passing unit + integration tests.

Headline risk

No cache / async

Every read hits MySQL; notifications and audit are synchronous, on the request thread.

Ceiling

Pool = 10

HikariCP maximum-pool-size: 10 caps DB concurrency well before the JVM saturates.

Fixed this cycle

IDOR closed

Candidate object-level authorization added (CandidateAccessGuard); staff/owner/admin policy enforced.

The platform comfortably serves ~100 concurrent users today and, with the recommended tuning (pool sizing, caching, async notifications, a read replica, and horizontal scaling behind a load balancer), is a realistic path to 1,000+. 5,000 concurrent users requires the full scale-out described in §8.

03 Backend performance review

Spring Boot service tier — architecture, concurrency, and the specific hot paths.

Architecture & strengths

  • Strict layer separation — controllers stay thin, services hold logic, repositories are Spring Data; requests/responses are immutable DTO records. Highly maintainable and testable.
  • Constructor injection everywhere (@RequiredArgsConstructor) — no field injection, so beans are immutable and thread-safe by construction.
  • Transactions scoped correctly with @Transactional (write) / @Transactional(readOnly=true) (read). open-in-view: false — no lazy-loading on the render thread, a common Spring performance trap already avoided.
  • Centralized error handling (GlobalExceptionHandler) maps exceptions to consistent status codes; the catch-all logs server-side and returns a generic body (no stack-trace leakage).

Weaknesses & opportunities

  • No caching layer high impact — no @EnableCaching/@Cacheable anywhere. Reference data (roles, skills, role-registration policy) and dashboard aggregates are recomputed from MySQL on every call. This is the single highest-leverage backend improvement.
  • No asynchronous processing high impact — no @EnableAsync. Notification and audit writes run inside the request transaction, adding latency to register/approve/login. Move to @Async or an outbox/queue.
  • N+1 in list mappers medium — RegistrationService.toSummary() and getDetail() resolve user, role, and company one row at a time. Batch with an IN-based fetch or a projection/JOIN DTO.
  • In-memory aggregation medium — DashboardController.countOffer() loads the entire offer table and filters in Java; replace with countByOfferStatus(...) (the ix_offer_offer_status index already exists).
  • Connection pool sizing high — DB_POOL_MAX_SIZE defaults to 10. Adequate for ~100 users; a bottleneck at 500+. Tune per instance and per CPU/DB capacity.
  • Logging — sane levels via env (LOG_LEVEL), WARN in prod. Ensure no PII in logs and prefer async appenders under load.

Thread safety & memory

Services are stateless singletons with injected dependencies — safe under concurrency. Memory risk is confined to the unbounded read paths (findAll() in dashboard/report aggregation): as those tables grow, heap pressure and GC pauses grow with them. Bounding every query (COUNT/aggregate in SQL, paginate lists) removes the risk.

04 Frontend performance review

React 19 + Vite + MUI SPA.

Strengths

  • Server-state caching done right — TanStack Query configured with staleTime: 30_000 and refetchOnWindowFocus: false (config/queryClient.ts), so navigation reuses cached data instead of refetching on every mount/focus.
  • Consistent data-fetching & forms — React Query + React Hook Form + Zod; Axios interceptor attaches the JWT centrally. Loading skeletons exist (StatCardSkeleton, etc.).
  • Component reuse — shared DashboardHero, StatCard, SectionCard, FormTextField primitives.

Weaknesses

  • No route-based code splitting high — no React.lazy/Suspense and no Vite manualChunks. Every role's pages ship in one bundle, so a Candidate downloads the Admin/Recruiter code too. Lazy-load routes per role to cut first-load JS.
  • Bundle discipline medium — with MUI + charts in a single chunk, initial payload grows with the app. Add code splitting + vendor chunking and measure with a bundle analyzer.
  • Token in localStorage security — XSS-exfiltratable (see §7); a rendering-performance-neutral but real hardening item.
  • Accessibility & responsive — MUI gives a reasonable baseline; a dedicated a11y pass (focus states, labels, contrast) is recommended before enterprise sign-off.

05 Database performance review

MySQL 8.4 (InnoDB), schema owned by Flyway V1–V34, validated by Hibernate on boot.

Strengths

  • Normalized, constrained schema — primary keys, foreign keys, and unique constraints (uq_user_email, uq_skill_skill_name, uq_candidate_user) enforce integrity at the DB, not just the app.
  • Targeted indexes — V24__create_indexes.sql adds status indexes (ix_job_job_status, ix_application_status, ix_offer_offer_status), a date index (ix_interview_interview_date), and composite lookup indexes (ix_approval_history_entity_type_entity_id, ix_audit_log_*). FK columns are auto-indexed by InnoDB.
  • Parameterized queries — no string-concatenated SQL; the registration search binds :q via LIKE CONCAT and whitelists sort columns (RegistrationService.SORT_COLUMNS), so native-query sort injection is not possible.
  • Pagination — list endpoints use Pageable / the custom ListResponse envelope rather than returning whole tables.

Weaknesses & recommended indexes

  • Leading-wildcard search medium — the registration/candidate search uses LIKE '%term%', which cannot use a B-tree index (full scan of the joined set). For larger datasets, add a FULLTEXT index on the searched name/email/company columns and switch to MATCH … AGAINST.
  • Composite index for the funnel medium — DashboardController.funnel(jobId) issues repeated countByJobIdAndApplicationStatus. Add ix_application_job_status (job_id, application_status) to cover it in one index.
  • Unbounded scans high — offerRepository.findAll() in the dashboard scales linearly with table size; convert to indexed COUNT … WHERE.
  • Concurrency / locking — approval and status transitions are short transactions; low contention today. As write volume grows, keep transactions short and consider optimistic locking (@Version) on hot mutable rows (application/interview status).

06 API performance review

REST design, payloads, and where caching/limits belong.

  • Design — resource-oriented, versioned (/v1/**), correct verbs and status codes; validation errors return 422 VALIDATION_FAILED, auth 401, authorization 403, conflicts 409. Consistent ErrorResponse shape.
  • Request validation — Jakarta Bean Validation on DTOs (@NotBlank, @Email, @Size); runs before controller logic.
  • Pagination / filtering / sorting — present on list endpoints (status filter, search, page/size, sortBy/direction on the registration queue).
  • Response payloads — DTO projections keep responses lean; avoid entity serialization.
  • Gaps: no rate limiting on any endpoint (notably /v1/auth/login — brute-force exposure); no HTTP caching headers (ETag/Cache-Control) on cacheable reads (reference data, dashboards); no bulk endpoints for multi-row admin actions.

08 Scalability & load analysis

The API is stateless (JWT), so horizontal scaling is available once the shared dependencies (DB pool, cache, file storage) are provisioned for it. Estimates below assume the current single-instance, pool-of-10 configuration unless noted.

ConcurrencyExpected behaviour (current config)Primary bottleneck
100 usersHealthy. Reads p95 < 300 ms; pool of 10 sufficient for short queries. CPU/heap comfortable.None material
500 usersPool contention begins; requests queue for connections on write-heavy or dashboard endpoints. Latency climbs on uncached aggregates.HikariCP pool + uncached dashboards
1,000 usersSingle instance saturates (pool waits, CPU on BCrypt + serialization). Needs 2–4 instances behind an LB, a cache, and pool tuning.Single node + DB round-trips
5,000 usersNot supportable as-is. Requires horizontal app tier, Redis cache, DB read replica(s), async notifications, and object storage for resumes.DB write path + fan-out; storage

Scale-out levers (no redesign, incremental)

  • Horizontal app scaling — stateless already; run N instances behind a load balancer (no sticky sessions needed).
  • Cache tier — Redis (or Caffeine per-node for reference data) for roles/skills/policy and dashboard aggregates.
  • Database — tune Hikari to instance count; add a read replica for reporting/dashboards; keep writes on primary.
  • File storage — move resumes from local disk to object storage (S3/Blob/GCS) so any instance can serve them.
  • Async — notifications/audit via @Async or a queue to shorten the request path.

11 Optimization recommendations

Backend

Add @EnableCaching + @Cacheable on reference data and dashboard aggregates; @EnableAsync for notifications/audit; replace findAll aggregation with COUNT queries; batch N+1 mappers.

Frontend

React.lazy + Suspense per route; Vite manualChunks for vendor/MUI/charts; bundle-analyze; move JWT out of localStorage.

Database

Add (job_id, application_status) composite; FULLTEXT for search; read replica for reporting; consider @Version on hot status rows.

Caching

Redis shared cache (cluster-wide) or Caffeine per-node for read-mostly reference data; short TTLs for aggregates.

Security

Per-request account-status re-check + token revocation; login rate limiting/lockout; server-side password complexity; resume content-type validation; strict CSP.

Cloud & DevOps

Containerize; deploy 2+ stateless instances behind an LB; object storage for resumes; secret manager for JWT/DB creds; extend CI to build image + deploy per env.

Monitoring

Scrape Actuator metrics into Prometheus/Grafana or an APM; alert on latency, error rate, and Hikari pool saturation.

Logging

Async appenders; correlation IDs per request; ensure no PII; keep prod at WARN/INFO.

14 Final conclusion

TalentAI is a well-architected, thoroughly tested recruitment platform whose foundations — layered Spring Boot, stateless JWT, a normalized and indexed MySQL schema, DTO-bound APIs, and a React Query frontend — are enterprise-appropriate. Its performance limitations are operational and localized, not structural: introduce a caching tier, make notifications/audit asynchronous, tune and scale the connection pool, bound the few unbounded aggregation/search paths, and scale the stateless app tier horizontally with a read replica and object storage.

Executed in the order given in §11, these changes raise the platform from a comfortable ~100-user pilot to a 1,000+-user production service without any redesign — and lay the groundwork for the 5,000-user tier. The build is suitable for pilot deployment now and for full enterprise rollout after the §8/§11 hardening.
